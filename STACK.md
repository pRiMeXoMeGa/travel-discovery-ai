# Features → Stack

Same 88 features as [FEATURES.md](./FEATURES.md), but each one answers three more questions:
**what technology it runs on**, **how we actually use that technology**, and **why we picked
it over the obvious alternative**.

Written in plain English. Where a choice was forced by a real constraint — 512 MB of RAM, a
free-tier quota, a 4-core laptop — the constraint is named, because that is usually the whole
reason.

For *how to demo* each feature, see [DEMO.md](./DEMO.md).

---

## The stack at a glance

| Piece | What we use | One-line reason |
|---|---|---|
| Frontend | Next.js 14 (App Router), React 18, TypeScript, Tailwind | Free hosting on Vercel with HTTPS and a CDN, and the whole app is one client-side surface |
| Maps | MapLibre GL JS | Open source, no API token, no per-view billing |
| Backend | FastAPI + Uvicorn, async Python, Docker on Render | Streaming answers need a process that stays alive; serverless would cut the stream off |
| Database | Postgres (Neon free tier), talked to with `asyncpg` | Listings, 200K review texts, summaries. Async driver so one slow query doesn't freeze the server |
| Vector search | Qdrant Cloud (free 1 GB) | Meaning-based search over listings + review summaries + memories |
| Embeddings | `fastembed` running bge-small (ONNX), 384 dimensions, on our own CPU | Costs nothing per query, needs no PyTorch, fits in 512 MB |
| Cache | Redis (Upstash free tier) | Travel searches repeat constantly; also stores paused trip plans |
| AI model | Gemini 3.1 Flash-Lite over plain REST, with Claude Haiku as a switchable alternative | Cheap, fast, returns reliable JSON and streams. REST because Google's old Python SDK is deprecated. To be precise: the provider is a config setting, not an automatic failover — one env var swaps every call over to Claude |
| Memory | `mem0ai` 2.0, storing into Qdrant, embedding locally | Gives us extract → store → recall → forget without writing it ourselves |
| Tool protocol | `fastmcp` 2.14, mounted inside the FastAPI app | Makes the platform usable by other AI agents, and lets us call outside tools |
| Graph workflow | LangGraph 1.2 with a custom Redis checkpointer | The trip planner has loops and a human approval step; the concierge does not |
| Tests | pytest + ruff + a Docker build in GitHub Actions; Playwright browser tests run locally | Catch regressions without spending a cent of AI quota. Playwright is deliberately out of CI — it needs the full data stack up, which a CI runner doesn't have |

## 1 · The booking product

| # | Feature | Stack used | How we use it | Why this way |
|---|---|---|---|---|
| 1 | Search 50,000 properties | Postgres + `asyncpg`; Qdrant for meaning-based queries | Plain filter searches are one SQL query. A sentence-shaped query is embedded locally and matched in Qdrant, then the full rows are fetched from Postgres | Keeping facts in Postgres and meaning in Qdrant means each store does what it's good at, instead of forcing one to do both badly |
| 2 | Filter by city, price, rating, type, amenities | SQL `WHERE` built in `backend/app/services/listings.py` | The filter clause is assembled from whichever fields arrived, with values passed as parameters, never pasted into the string | Parameters make SQL injection impossible, and one shared builder means the API, the AI agents and the MCP tools all filter identically |
| 3 | Sort by price, rating, popularity, distance | SQL `ORDER BY`; distance is the haversine formula written directly in SQL | For "near this point" we compute `6371 * 2 * ASIN(SQRT(...))` inside the query and sort on it | The database sorts all 50,000 rows and returns 20. Doing it in Python would mean pulling every row over the network first |
| 4 | Pagination | SQL `LIMIT` / `OFFSET` with a separate count query | Page and page size come from the URL, so a result page can be linked and refreshed | Standard, cheap, and correct at this size. Cursor pagination would be over-engineering for 50K rows |
| 5 | Map with price labels | MapLibre GL JS + custom HTML markers | Each listing becomes a small HTML element positioned by MapLibre, showing its price | MapLibre is a free fork of Mapbox with no token and no view billing. HTML markers let us style a price pill with Tailwind instead of fighting a canvas API |
| 6 | Pin clustering | Our own grid-based clustering in React (`MapView.tsx`) | Pins are bucketed into grid cells sized by zoom level, and re-bucketed whenever zooming ends | MapLibre's built-in clustering only works for canvas layers, not the HTML price pills we want. ~30 lines of grid maths kept the design |
| 7 | "Search this area" | MapLibre's map centre → the existing distance sort | We read the centre point of the visible map and re-run the search sorted by distance from it | It reuses the haversine sort that already exists (feature 3) rather than adding a bounding-box filter. Honest limitation: it **re-ranks** the results, it does not clip them to the visible box, so a listing just off-screen can still appear near the top |
| 8 | Hover a card → its pin lights up | Shared React state between list and map | One "hovered id" value lives above both components, so each reacts to it | Two components reading one value can never disagree. Event wiring between them could |
| 9 | Listing detail page | Next.js App Router dynamic route `/listings/[id]` | The page fetches one listing plus its calendar and reviews | File-based routing means the URL and the code live in the same place |
| 10 | At least 4 photos per listing | Ingestion pipeline + `ingestion/photo_pool.json` | The source data ships one photo per listing, so we add extras drawn deterministically from a pool of real photos from the same city | Same listing always gets the same gallery, so screenshots and tests stay stable. All images are real Airbnb CDN URLs, none invented |
| 11 | 30-day availability calendar | Pure Python `sha256` hash — `backend/app/availability.py` | `hash(listing_id + date)` decides whether a night is free and nudges the price ±15% around the real base price | The real calendar exports are 426 MB+ and one city has no prices at all. Hashing gives stable, repeatable results and saves ~18 million database rows |
| 12 | Price breakdown for a date range | The same hash function, summed over nights | Every night is priced individually and totalled | Because it's a function, not a table, the total is always consistent with the calendar you just looked at |
| 13 | Neighbourhood price percentile | Postgres ranking query, run once at ingest | Every listing is ranked against the other prices in its own neighbourhood, and the resulting position (0–100) is saved on the row | Computing it at ingest means the page just reads a number. Doing it per request would rank 50,000 rows on every page view |
| 14 | Browse reviews, 20 per page | SQL `LIMIT` / `OFFSET` on the `reviews` table | Paged straight from Postgres | 200,000 rows is far too many to send at once, and nobody reads past page two anyway |
| 15 | Filter reviews by language | A `language` column filled at ingest by `langdetect` | Detected once when the review is loaded, then filtered with a plain equality check | Detecting language at read time would cost CPU on every request for a value that never changes |
| 16 | Search review text by topic | A plain case-insensitive "contains this word" match in Postgres | Typing "location" keeps only that listing's reviews whose text contains the word | Deliberately simple, because it runs over one property's ~10 reviews. The heavier search index is saved for the AI review agent, where *ranking* matters and a plain contains-match wouldn't do |
| 17 | Wishlist that survives reloads | Browser `localStorage` + a React context | Hearted ids are kept in one array in the browser and read back on load | There is no sign-in in this project, so there is nowhere on the server to attach a wishlist to. Being honest about that beats faking an account |
| 18 | Compare 2–4 listings | `POST /api/batch/compare` | One request fetches all the listings and builds the comparison matrix | One round trip instead of four, and it lets the AI verdict be produced in the same call |
| 19 | AI verdict on a comparison | Gemini, up to 5 calls | Each property's reviews are summarised, then one final call weighs them against each other and recommends | Reading real review evidence per property first is what stops the verdict being a rewrite of the price table. It is the most expensive endpoint we have, which is exactly why the MCP tool version skips it |
| 20 | Correct currency per city | A small lookup table in `frontend/lib/currency.ts` | Amsterdam and Lisbon show €, Los Angeles shows $ | The source prices really are in local currency. Converting them would invent an exchange rate and make the number less true, not more |
| 21 | Removable filter chips | React state mirrored into the URL (`lib/search-state.ts`) | Active filters render as chips; removing one rewrites the URL, which re-runs the search | Keeping filters in the URL makes search results shareable and makes the browser back button work properly |

## 2 · The data underneath

| # | Feature | Stack used | How we use it | Why this way |
|---|---|---|---|---|
| 22 | Real Inside Airbnb data | The detailed `listings.csv` / `reviews.csv` exports | 50,000 listings and 200,000 reviews across Amsterdam, Lisbon and LA | Real review text is what makes the AI layer worth building. Generated reviews would have made every AI claim meaningless |
| 23 | Re-runnable ingestion pipeline | Python in its own Docker service (`ingestion/`) | Parse → clean → enrich → embed → load, and it can be run again safely | Anyone can rebuild the whole dataset from the raw CSVs with one command. A pipeline that only works once isn't a pipeline |
| 24 | Price cleaning | Python parsing at ingest | `$1,234.00` becomes `1234.0`; missing prices are filled with the median | Prices are used for filtering, sorting and budget maths. One text value would break all three |
| 25 | Amenity normalisation | A hand-built 18-term vocabulary in `ingestion/enrich.py` | Hundreds of messy free-text amenities collapse into terms like `wifi`, `kitchen`, `parking` | Users pick from a checkbox list. That list can't have 400 near-duplicate entries |
| 26 | Language detection | `langdetect` | Every review gets a language code at ingest | Enables the language filter, and lets the review sampler deliberately include non-English voices instead of quietly dropping them |
| 27 | Aspect sentiment per review | Keyword heuristic with negation handling, in Python | Each review is scored −1..+1 on cleanliness, location, value, noise and staff, and "not clean" is caught as negative | Scoring 200,000 reviews with an AI model would have taken far more free-tier quota than exists. The AI path is written and tested — it just isn't affordable at this volume, and we say so rather than half-running it |
| 28 | A review summary for all 50,000 | Ingestion (no AI) | The first two reviews the database returns are truncated at 120 characters each and stitched together | Every property needs *something* on its page, and this is instant and free. It is not clever — there is no selection logic, and it can cut off mid-word — which is exactly why feature 30 exists to stop it being labelled as AI |
| 29 | 1,286 genuinely AI-written summaries | `scripts/backfill_summaries.py` + Gemini + Qdrant | The properties with the most reviews get a real model-written summary, and their vectors are rebuilt so search matches the new text | Reviews are capped at 10 per property in this corpus, so "most evidence" saturates at 1,286. Going further would rank on a tiebreak, not on real evidence |
| 30 | Honest labelling of summaries | A `provenance` column carried through the API to the UI | Only rows marked `llm` get the sparkle and the words "AI Review Summary"; everything else says "quoted from reviews" | This is the fix that mattered more than the backfill itself. Before it, 48,714 stitched-together extracts were labelled as AI-written — a false claim on every page |
| 31 | Deterministic calendar | The same hashing functions copied into both the backend and the ingestion service | The three functions that decide availability and price are kept identical in both copies; the backend's copy adds one extra helper for the detail-page calendar | Ingestion and the API are separate services and can't import from each other, so the logic is duplicated with a "keep these in sync" warning at the top of both. If they ever drifted, a listing would be bookable on one screen and full on another |
| 32 | Semantic search index | Qdrant + `fastembed` (bge-small, ONNX, 384-dim) | Listings and per-property summaries are turned into vectors on our own CPU and stored in Qdrant, cosine distance | No embedding API bill, no PyTorch, and 384 dimensions keeps the whole corpus inside Qdrant's free 1 GB. The same model runs at ingest and at query time, so the vectors are directly comparable |

## 3 · Natural language & the concierge

| # | Feature | Stack used | How we use it | Why this way |
|---|---|---|---|---|
| 33 | Natural-language search bar | Gemini, asked for strict JSON (`agents/intent.py`) | Your sentence goes in, a structured filter object comes out, and it fills the normal filter UI | The AI's job stops at understanding. The search itself is ordinary SQL and vector search, so a bad parse can never invent listings |
| 34 | Plain-English dates | Gemini, given today's date as a reference | "late June" is resolved to real ISO check-in/check-out dates before anything else runs | Downstream price maths needs exact dates. Resolving them once, up front, keeps costs deterministic |
| 35 | Extracts city, budget, party size, amenities, type, area | A fixed JSON schema in the intent prompt | The model must fill named fields; every value is then re-checked against real cities, amenities and neighbourhoods in Python | Anything the model returns becomes a hard database filter, so an unchecked value could silently return zero results. We validate rather than trust |
| 36 | Shows what it understood, as chips | React, in two places | The search bar shows a read-only "Understood: …" summary of the parse; the fields it actually applied then appear as the normal removable filter chips (feature 21) | You can see a misunderstanding and correct it by removing the filter it produced. The parse preview itself is deliberately read-only — the filter row is the one place filters get edited, so there is only ever one control that matters |
| 37 | Says what it could *not* do | An `unsupported` field in the same JSON schema | Requests we can't honour ("a castle on the moon") are named back to you, after filtering out anything that actually did land in a real field | Silently dropping part of a request is the worst failure mode here — you'd think it searched for something it never searched for |
| 38 | Family requests prefer whole homes | Python re-ordering plus an SQL `ORDER BY` clause | When the wording suggests a family and no property type was stated, entire homes sort above private/shared rooms | A family of four in a shared room is a bad result. But hiding rooms entirely would be us overriding you, so they're ranked lower, not removed |
| 39 | Neighbourhood nicknames | A 161-entry alias table → Qdrant filter conditions on the indexed `neighbourhood` field | "near the centre" or "downtown" resolve to the real neighbourhood names for that city | It reuses an index that already exists — no new geo index, no re-uploading the whole collection. Before this, "downtown" was parsed and then thrown away |
| 40 | Streaming answers, word by word | `sse-starlette` on the backend, `fetch` + `ReadableStream` in the browser | The backend yields events as they happen; the browser reads the stream as it arrives | We use `fetch` rather than the browser's `EventSource` because our endpoint is a POST with a real request body, which `EventSource` cannot send |
| 41 | Live step timeline | Our own async-generator orchestrator (`agents/orchestrator.py`) | Every stage emits a start/done/error event on the same stream as the answer, so the panel shows each one turning from spinner to tick. The per-step timings and token counts are recorded alongside and arrive in the final trace (feature 72), not on each step | Waiting 8 seconds at a blank screen feels broken; watching it work feels fast. The numbers are kept out of the panel on purpose — they're for debugging and for the production smoke checks, not for a traveller booking a flat |
| 42 | Handles two questions at once | A keyword + structure classifier that returns a *list* of routes | "Find me a place **and** tell me what guests complain about" runs both the search and review pipelines, then merges their results before answering | Picking one route meant silently ignoring half the question. Running both costs no extra AI call, because the classifier is plain Python |
| 43 | Review answers cite real reviews | Postgres full-text search (a word index over all 200,000 reviews) + Gemini | The most relevant reviews for a property are ranked in Postgres — deliberately sampling both positive and negative, and more than one language — then the model summarises them and tags each claim `[r1]`, `[r2]` | The citation points at a real database row you can go and read. That's the difference between a grounded summary and a confident guess |
| 44 | Admits when it doesn't know | An explicit abstention path in the shared review service | No reviews means the answer is "I don't have evidence". Over MCP that also comes back as a machine-readable `abstained` flag with a reason; in the chat panel it is the sentence itself | A summary of nothing is the most damaging thing a review feature can produce, because it looks exactly like a real one. Another *agent* can't read tone, so it gets the flag; a human reading the answer doesn't need one |
| 45 | Multi-stop trip planning | `agents/itinerary.py` + Gemini + the normal retrieval path | The model proposes the shape of the trip; the actual stays are retrieved by real search for each segment | The model decides structure, the database decides facts. That's why the plan can't contain a property that doesn't exist |
| 46 | Budget awareness | Plain Python arithmetic | Nightly prices are summed across segments and compared to your stated budget | Never ask a language model to add up money. Arithmetic is free and exact in Python |
| 47 | Resists prompt injection | Prompt structure — retrieved text and memories go in the *user* message, inside a delimited block, never the system prompt | Instructions found inside data are treated as data | The system prompt is the only place the model should take orders from. Anything else is content, including content that's phrased as a command |
| 48 | Graceful failure | Try/except around every agent step | A broken step records the error, emits it on the stream, and lets the rest continue | A failed search should say "search failed", not quietly produce an answer with nothing behind it |

## 4 · Memory (it remembers you)

| # | Feature | Stack used | How we use it | Why this way |
|---|---|---|---|---|
| 49 | Remembers preferences between sessions | `mem0ai` 2.0, storing into Qdrant, embedding locally with our own fastembed adapter | Memories are saved against a traveller id and recalled at the start of the next turn | mem0 gives us extract/store/recall/forget for free. We swap its embedder for ours so there's no second embedding bill and no second model in RAM. Identity is a browser-stored UUID — same-browser persistence, not an account |
| 50 | Standing rules become hard filters | Gemini extraction + tagged metadata + Qdrant filter conditions | "never show me shared rooms" is stored as a structured rule (`field`, `value`, `never`) and applied to every later search | Rules are recalled **by their tag, not by similarity**. A promise you made the system keep cannot depend on a fuzzy match scoring high enough today |
| 51 | Understands direction correctly | The same structured rule shape, with an explicit direction | "allergic to dogs" and "always travel with my dog" produce opposite rules on the same field | Storing the sentence alone would leave the direction to be re-guessed on every read. Storing the direction settles it once |
| 52 | Tells you when it used your memory | A disclosure line in the answer prompt plus a flag on the response | The answer states which saved preferences were applied | Invisible personalisation is indistinguishable from a bug. If your results narrowed, you should know why |
| 53 | Memory panel with badges | React section inside the concierge slide-over | Shows each memory, a `never · Shared room` style badge for enforced rules, and a match percentage | You can't trust or correct what you can't see. The raw similarity score was shown as `0.83` at first — now it reads "83% match" with an explanation, because a bare decimal tells a user nothing |
| 54 | Forget button | `DELETE /api/memory/{id}` | Removes the memory, and the next search immediately reverts | If you can't delete it, it isn't your memory — it's just data we're holding |
| 55 | Revoke by talking | A second field in the intent JSON schema | "actually shared rooms are fine now" is recognised as a revocation and the rule is dropped | Making someone hunt for a settings panel to undo something they said in conversation is bad design |
| 56 | This turn beats memory | Precedence rules in Python, before the search runs | Anything you state now overrides anything remembered | Memory is context, not a veto. The most recent statement is the most likely to be true |
| 57 | Memory can never set city, dates or budget | A guard that drops memory-sourced values for those three fields | If a value traces to memory and not to your current words, it's discarded | Those three become hard filters. Letting an old sentence set your city would hijack the search — and the guard is written to fail by *widening* results, never by silently narrowing them |
| 58 | Trip memory kept separate | A second mem0 scope keyed by trip id | Trip facts are derived from the current search, not copied from long-term preferences | Two stores holding copies of the same fact will eventually disagree. One derives from the other instead |

## 5 · Human-in-the-loop planner

| # | Feature | Stack used | How we use it | Why this way |
|---|---|---|---|---|
| 59 | Plan mode | LangGraph 1.2 (`backend/app/planner/`) | A separate graph flow, reached by an explicit Ask / Plan toggle in the UI | Mode is chosen by you, not auto-detected. If a classifier sent you here by surprise, the planner stopping to ask a question would look like a crash |
| 60 | Stops and asks for approval | LangGraph's `interrupt()` | The graph pauses mid-run, the stream ends with "awaiting input", and `POST /api/planner/resume` picks it up | A real human checkpoint, not a fake "confirm?" prompt after the work is already done |
| 61 | Approve or Adjust | A conditional edge back into the planning node | "somewhere quieter" loops back, replans, and asks again | Editing by conversation beats starting over |
| 62 | Survives a server restart | A ~260-line Redis checkpointer we wrote over the existing Upstash client | Graph state is saved to Redis after each step, with a 7-day expiry | The free hosting tier puts the server to sleep after 15 minutes idle — exactly the window in which you're deciding. We use Redis rather than LangGraph's Postgres checkpointer because that would add a *second* Postgres driver to a 512 MB box for a few small JSON blobs |
| 63 | It can loop | Cycles in the graph, capped by `MAX_REPLANS` | An empty or over-budget plan relaxes a constraint and tries again | Loops are the reason this flow uses a graph at all. The cap exists because an impossible budget would otherwise bill AI calls forever |
| 64 | Budget relaxation is disclosed | A flag carried through the graph state into the answer | If it had to loosen your budget to find anything, it says so | A plan that quietly ignores your budget isn't a plan, it's a surprise |

## 6 · Tool use, both directions

| # | Feature | Stack used | How we use it | Why this way |
|---|---|---|---|---|
| 65 | The platform is an MCP server | `fastmcp` 2.14, mounted **inside** the existing FastAPI app at `/mcp` | Other agents — Claude Desktop, for instance — connect and call our tools | Mounting rather than running a second service means it shares the same database pool, cache and vector client: one deploy, one cold start, one keep-warm ping. A second free service would have used up the monthly hosting allowance |
| 66 | Six tools exposed | fastmcp tool definitions backed by our shared service layer | search, detail, availability, compare, review synthesis, itinerary | They call the same code the website calls, so an external agent can never get a different answer than a browser would. Each tool's description is written *for the calling model* — stating its grounding guarantee, its AI cost and its real enum values — because that description is the only thing the agent sees when deciding whether to call it |
| 67 | Password-protected, fails closed | A shared key checked in a layer that sits *in front of* the tool server, before any tool code runs | Wrong key or no key → 401. **No key configured at all → 503**, not an open endpoint | Doing the check in front of the library, rather than with the library's own auth feature, means it keeps working when that feature changes between versions — and it has. It fails closed because two of the six tools spend real AI quota |
| 68 | Rate-limited | An in-process per-key request cap | Only the two AI-backed tools are capped | A misbehaving external agent shouldn't be able to burn a month of quota in an afternoon |
| 69 | Cheap tools stay cheap | A deliberate second code path | `compare_listings` over MCP returns the matrix only — never the AI verdict the website's compare button produces | An agent browsing a few options must not silently trigger five AI calls per comparison |
| 70 | We also *consume* an external tool | `backend/app/weather.py` acting as an MCP client | One call per trip plan (not per stay) fetches a forecast, and the note is built **from the returned numbers in Python** | We build the note deterministically rather than passing the server's text through, because that server actually returns instructions-for-an-LLM plus raw hourly JSON. Same grounding rule as everywhere else |
| 71 | If weather is down, plans still work | A 3-second hard timeout, a 6-hour Redis cache, and full silent degradation | Failure emits a visible `weather_mcp` step in the trace, and the plan continues without a forecast | A third-party outage can never break a trip plan. And because the weather service is off by default locally, the *normal* local run exercises the degraded path — which is the one that has to work |

## 7 · Engineering you can see

| # | Feature | Stack used | How we use it | Why this way |
|---|---|---|---|---|
| 72 | Full request tracing | Our own `RequestTrace` object, on the SSE stream | Every answer reports which steps ran, how long each took and how many tokens it used | Built into the response rather than a separate dashboard, so the evidence is always attached to the thing it describes |
| 73 | Token counts are measured | The provider's own `usageMetadata`, read off the final streaming frame | Real counts from Google/Anthropic, marked `measured`; the old estimate is kept only as a labelled fallback | The previous version counted stream chunks and called it tokens. It was wrong in a way nobody would notice, which is the worst kind of wrong |
| 74 | Caching | Redis (Upstash), with a different expiry per kind of thing | Search results 2 minutes, the concierge's retrieval step 5 minutes, listing pages / review summaries / comparison verdicts 1 hour, weather 6 hours — each stored under a key that includes **every** input that changes the answer | Expiry follows how fast a thing goes stale against what it costs to rebuild: a search is cheap and moves while ingestion runs, an AI review summary is expensive and barely changes. The "every input" rule was learned twice, painfully — a key missing one input once served personalised results to the wrong person, and later made a working feature look completely useless |
| 75 | Degrades gracefully | Try/except at each external boundary | Turn Qdrant off and search still works from Postgres alone | Free-tier services do go down. Losing semantic ranking is acceptable; losing search is not |
| 76 | Automatic retries | `httpx` with exponential backoff and jitter in `app/llm.py` | Retries on 429/500/502/503/504 **and 529**, roughly 0.4s → 0.8s → 1.6s | Model providers rate-limit under load constantly. 529 was added after Anthropic's "overloaded" response was failing outright while ordinary 503s retried fine |
| 77 | Streaming works through proxies | The `X-Accel-Buffering: no` header plus `Cache-Control: no-cache` | Set on every streaming response | Without it, hosting proxies buffer the whole answer and deliver it in one lump — the stream still "works", it just stops streaming |
| 78 | Keep-warm ping | A GitHub Actions scheduled workflow, every 10 minutes | Pings `/health`, which touches no database and no AI model, and warns if the reply took over 5 seconds | Free hosting sleeps after 15 minutes; waking up costs the next visitor ~56 seconds. Note that GitHub only runs schedules from the default branch — while this file sat on a feature branch it fired nothing at all |
| 79 | Fits in 512 MB | Measured with `docker stats`, subsystem by subsystem | 193 MB idle → 406 MB with the concierge → 409 with memory → **479 MB** with the planner loaded | The memory limit is a hard gate, not a guideline. Every dependency choice above — ONNX not PyTorch, 384 dimensions not 1536, Redis not a second Postgres driver — was made against this number |
| 80 | Reranking: built, measured, switched off | `fastembed`'s ONNX cross-encoder, behind `RERANK_ENABLED=false` | Measured to change 2 of every 3 visible results — a real effect — but it needs **+156 MB** and 20.8s to load, and 1,064 ms to rerank 50 results | 479 + 156 is well over 512: the server would be killed. So it ships lazily loaded and disabled, and turns on with one environment variable on a 1 GB box. The measurement script deliberately does **not** claim the new order is *better* — nothing in it knows the right answer |
| 81 | Cost measured per query | `scripts/benchmark.py` × the provider's published prices | Real token counts × real rates: ~$0.0006 per NL search, ~$0.0011 per full concierge turn, $0 for ordinary filter search | Three earlier versions of this table were wrong — placeholder prices, hand-read token counts, and a "per turn" figure that wasn't per turn. Now every number traces to a measurement |
| 82 | Model benchmark | The same script across models and golden queries | Compares accuracy, speed and cost using field-by-field checks and citation validity | No AI judging AI. An LLM judge would add a second unmeasured system to the thing we're trying to measure |
| 83 | 289 backend tests | pytest + ruff, with the AI model mocked | Runs in seconds, costs zero quota, blocks the merge if it fails | A test suite that costs money to run is a test suite people stop running |
| 84 | 16 browser tests | Playwright against the real UI | Drives real clicks through search, map, detail, wishlist, compare, concierge and planner | Everything else can pass while the page is blank. One of our worst bugs passed types, build, unit tests and API checks — only a browser caught it |
| 85 | Continuous integration | GitHub Actions | Lint, tests and a Docker build on every push | The Docker build step matters as much as the tests: "works on my machine" is exactly what the container is meant to rule out |
| 86 | End-to-end production check | `scripts/prod_smoke.py` — 41 assertions | Runs against the **live** deployment and asserts on response *content*: real citations, real provenance flags, a dealbreaker actually binding | Deliberately not in CI, because it spends real AI quota. And it checks content rather than status codes — a 200 that returns nothing useful is still a failure |
| 87 | Runs locally with one command | Docker Compose | `docker compose up -d` brings up Postgres, Qdrant, Redis, backend and frontend | Five services, one command, no setup instructions to get out of date |
| 88 | Deployed and live | Render (backend, Docker) + Vercel (frontend) + Neon + Qdrant Cloud + Upstash | Infrastructure declared in `render.yaml`; both hosts build from the default branch | All free tiers, and each was chosen for one specific reason: Render because streaming needs a long-lived process, Vercel because the frontend is static-ish, and managed databases so there's no VM to maintain |

## Choices we deliberately did *not* make

Sometimes the interesting decision is the thing that isn't in the stack.

| Not used | What we did instead | Why |
|---|---|---|
| PyTorch / sentence-transformers | `fastembed` on ONNX | PyTorch alone is bigger than the entire 512 MB memory budget |
| A paid embedding API | Local embeddings on our own CPU | Zero cost per query, and no third party in the search path |
| Vector-embedding all 200,000 reviews | Postgres full-text search, plus per-property summary vectors | Embedding them on a 4-core laptop is roughly 15 hours. The cost is weaker cross-property review search, and it's written down as a known limitation rather than hidden |
| Mapbox | MapLibre | No token, no per-view billing, same API |
| `react-markdown` | A ~130-line renderer for the four things the model actually emits | The answer bubble re-renders on every streamed token; a full markdown parse per keystroke is the wrong shape of cost for a 40 kB dependency |
| LangGraph for the concierge too | A custom async-generator orchestrator | The concierge has no loops and no waiting on a human. What it needs is per-step streaming and exact token accounting — a few lines in a generator, awkward to retrofit onto a framework's callbacks |
| LangGraph's Postgres checkpointer | ~200 lines of Redis checkpointer | It would install a second Postgres driver alongside the one we already use, for a handful of small JSON blobs |
| Google's `google-generativeai` SDK | Plain REST calls via `httpx` | The SDK is deprecated, and REST lets us swap in Claude as a fallback behind the same interface |
| A real login system | A browser-stored UUID | Accounts are explicitly out of scope. So we say plainly that "remembering you" means remembering this browser — clear your site data and the memory is gone |
| OCR of booking documents | Nothing | The one planned feature deliberately cut for time. Cut on purpose, not failed quietly |
